# 自然言語検索 PoC 検証記録

実施日: 2026-09-22 / Jev 0.2.0

[実装計画](natural-language-search-implementation-plan.md)に沿い、管理画面の既存Jev検索を、OpenAI embeddingによる候補取得とJevのNoul・Scoreによる評価へ置き換えた。MT本体のファイルは変更していない。`mt:JevEntries` は保留。

## 実装した範囲

| 要件 | 実装・確認方法 |
| --- | --- |
| OpenAIキーと候補数の設定 | 両APIキーの末尾4文字表示、未編集時の保持、更新・削除、候補数1〜500の検証。既定値は50 |
| embedding生成・保存 | `text-embedding-3-large` / 3072次元。全文を1入力とし、float32 little-endian BLOBをMTの独自モデルに保存 |
| 初期生成 | `tools/Jev/build-index`。サイト・種類の絞り込み、同一内容のスキップ、`--force`、失敗時の停止と再実行 |
| 保存・削除 | 記事・ページ・コンテンツデータのモデルフック。内容変更時だけ再生成。失敗時は古い索引を残さず、記事の保存自体は取り消さない |
| 候補取得 | MTの検索範囲・権限を適用した後にベクトル上位K件を選択。未索引・古いハッシュは検索時に生成せず除外 |
| Jev評価 | 文書を共有するNoul・Scoreの2質問。Noulで条件適合を判定し、Score降順→類似度降順→ID昇順。表示上限は評価・並べ替え後に適用 |
| 文書化 | 日本語・HTML・選択肢・カテゴリー・タグ・参照フィールド。共有embeddingには権限依存の参照先ラベルを含めない |
| 検索UI | 「自然言語で検索」。項目指定・大小文字・正規表現・置換を無効化。OFFで通常検索に戻る。ヘッダー既定ON/OFFを維持 |
| エラー処理 | HTTP期限、検索全体の期限、長文・不正回答・不正ベクトルを検証。失敗時に部分結果や自動全件評価を返さない |
| 配布 | 既存のMakefile.PL / compose.yml / Dockerfileを使用。CLIと新規モジュールを含むtar.gz・zipを生成 |

専用ベクトルDB、ジョブ、進捗画面、自動復旧、排他制御、要約、チャンク分割、結果キャッシュは追加していない。

## 自動テスト

MT9のチェックアウトとPerl 5.38の開発コンテナーを使用。APIはモックし、実際のMTモデル・検索ハンドラー・テンプレート描画を通して確認した。既存の開発用MySQLデータを使わず、MySQLのテストには専用の一時コンテナーを使用した。

| 実行環境 | 結果 |
| --- | --- |
| SQLite / admin2025 | 8ファイル・175項目 PASS |
| SQLite / admin2023 | 8ファイル・175項目 PASS |
| MySQL 8.0.32 / admin2025 | 8ファイル・175項目 PASS |
| JavaScript / jsdom | 9テスト PASS |

Perlの項目数は `prove` が集計するトップレベルの数。各subtest内にも複数の検証を含む。

以下はMTのテスト依存が利用できる環境での再現コマンド。`MT_HOME` はMT本体のディレクトリを指定する。

```sh
MT_HOME=/path/to/movabletype MT_TEST_BACKEND=SQLite prove -j1 plugins/Jev/t/*.t
MT_HOME=/path/to/movabletype MT_TEST_BACKEND=SQLite MT_TEST_ADMIN_THEME_ID=admin2023 prove -j1 plugins/Jev/t/*.t
NODE_PATH=/path/to/movabletype/node_modules node --test plugins/Jev/t/*.test.cjs
```

MySQLの場合、必ずテスト専用サーバーを使用する。MTのテスト環境はテスト用データベースを作成・初期化する。

```sh
MT_HOME=/path/to/movabletype MT_TEST_BACKEND=mysql \
  MT_TEST_DSN='dbi:mysql:host=TEST_MYSQL_HOST;user=TEST_USER' \
  prove -j1 plugins/Jev/t/*.t
```

主なテスト:

- `openai.t` / `client.t`: 送信JSON、認証、次元、数値、Noul・Scoreの回答型、長文の分割・拒否、期限、HTTPエラー。APIキーや応答本文をエラー表示に含めない。
- `embedding.t`: APIを呼ばないスキーマ初期化、BLOB往復、保存時更新・削除、同一内容の再利用、失敗時の本文保存と索引除去。
- `cli.t`: 別プロセスでCLIを実行。3種類、カテゴリー・タグのあるコンテンツデータ、範囲指定、再実行、強制生成、途中失敗を確認。
- `search.t`: サイト・子サイト・日付・公開状態・権限、既知のベクトルによるtop-K、Score順、低Noul・高Scoreの除外、表示上限、未索引、例外後の通常検索・置換。
- `references.t`: 参照先権限、共有embeddingからの機密ラベル除外、ユーザー・管理画面言語に依存しないハッシュ。
- `config.t`: 設定の描画、キーのマスク・保持・更新・削除、ヘッダー既定値、入力値検証。
- JavaScript: ヘッダー送信、Enter・IME、ON/OFF、検索種類、DOM再描画、検索オプションの無効化・復元、両キー編集欄の独立性。

MySQLでは `mt_jev_embedding_object` が `(object_type, object_id)` のUNIQUEインデックスになっていることも確認した。

## 2026-09-23 追記: Jevの2並列化

既定の5件ずつというバッチを維持し、Perl標準の `fork` で最大2つの子プロセスから既存LWPクライアントを呼び出すよう変更した。追加のCPAN依存はない。文書化・権限確認・DB操作・結果描画は親プロセスで行う。

追加検証:

- SQLite / admin2025: 9ファイル・180項目 PASS。admin2023も検索統合テスト26項目を含めてPASS。
- `parallel.t`: 実際にforkし、HTTP応答だけをモック。50文書・10リクエストの送信JSONが逐次版とバイト単位で一致すること、最大同時数2、ID別の回答・使用トークン数の一致を確認。
- 429の再試行待ちの間にもう一方が進むこと、応答順が前後してもIDの対応が維持されることを確認。
- HTTPエラー・検索全体の期限切れでは、待機中の子プロセスを終了・回収し、呼び出し終了後に処理が継続しないことを確認。空入力・単一バッチではforkしない。
- `search.t`: API評価だけをモックし、実際のCMS検索からforkを実行。全回答を集めた後のScore順、親プロセスでのDB再読込、後続の通常検索を確認。
- 配布用tar.gz・zipを再ビルドし、18ファイルすべてが作業ツリーと一致することを確認。

50文書・各HTTP応答に80ミリ秒の待ち時間を入れたモック計測では、逐次0.897秒、2並列0.457秒だった。これは通信待ち部分の動作確認であり、実APIや検索画面全体の短縮時間を示すものではない。課金を伴う実API計測は行っていない。


## 2026-09-23 追記: 数値処理と接続再利用の最適化

保存済みベクトルは数値専用の処理に変更し、NaN等の検出と再正規化を維持した。JevのHTTPS接続は各子プロセスで再利用する。既存DBの1,000件で従来の全成分・類似度と一致し、`keepalive.t` では実際のローカルHTTP接続の再利用とfork前の切断を確認した。SQLite / admin2025の全10ファイル・197項目 PASS。

同じMySQL・実API・検索文で検索処理とHTML生成は6.483秒から3.410秒になった。各1回の測定で、アプリ初期化・認証・ブラウザー等は含まない。[詳細と測定条件](search-performance-2026-09-23.md#最適化後の実装と再計測)を参照。

## 2026-09-23 追記: 並列数の設定化（既定5）

システムのプラグイン設定に「Jevの並列数」を追加した。1〜10の整数を指定でき、未設定時は5、1なら逐次実行する。子プロセス数は空でないバッチ数までに抑える。

- SQLite / admin2025: 全10ファイル・213項目 PASS。admin2023も設定・検索の2ファイル・70項目 PASS。
- 設定未保存時の既定値5、1と10の保存・再表示、不正値の拒否と既存設定の保持、CMS検索クライアントへの反映を確認。
- HTTP応答だけをモックし、実際のforkで既定5並列と1/2/4/5/10並列を確認。50文書・10リクエストの送信JSON、ID別の回答、使用トークン数は逐次評価と一致。4並列ではバッチを均等に割り切れない場合も確認した。
- 空・単一バッチと並列数1ではforkしない。設定10で3バッチなら子プロセスは3つだけ生成する。逐次実行でも検索の共通期限を維持する。
- 既定5並列で失敗・期限切れ時の全子プロセス終了・回収を確認。実際のローカルHTTPサーバーに対し、5ワーカーがそれぞれ独立した接続を再利用することも確認。
- tar.gz・zipを再ビルドし、収録18ファイルが作業ツリーと一致することを確認。

今回の変更では実APIでの所要時間を再計測していない。上記の3.410秒は2並列での過去の測定値。

システム設定でJevまたはOpenAIを選べるようにした。既定はJev。OpenAIの評価用モデルは `gpt-5.4-mini` を初期値とし変更できる。既存OpenAIキーとembedding索引を共用する。

- SQLite / admin2025: 全11ファイル・221項目 PASS。admin2023: 設定・検索の2ファイル・74項目 PASS。

- CMS検索で、TypeSafeキーなしのOpenAI評価、設定モデルと並列数の受け渡し、OpenAIへの送信先表示、しきい値による絞り込みを確認。OpenAIキー未設定なら送信せず、評価エラー時はJevへの自動フォールバックや部分結果表示を行わない。
- `evaluator.t`: Responses APIのJSON Schema、Unicode、ID対応、入力の自動切り詰め無効、拒否/中断/欠落/重複/余分なID/不正値の拒否、サイズ分割、実際のforkによる応答集約、429/5xxの再試行、共有期限、秘密情報を含まないエラーを検証。

### 実APIの少量確認

`xt/openai-evaluation-live.t` を既存の設定済みキーで実行し、架空の短い3文書だけをOpenAIへ送信した。実際の記事本文や索引は送信・変更していない。Responses APIを3回呼び、5項目 PASS。

- 「移行で実際に困ったことがあり、料金・費用への言及がない」という条件で、該当文書を採用し、困難の否定と文末の料金記載をそれぞれ除外できた。
- 単一バッチと、2バッチの並列評価の両方が成功した。
- `gpt-5.4-mini`、入力合計1,127トークン。単一バッチ3.604秒、続く並列評価1.721秒。架空の短文で各1回の測定であり、候補50件の検索画面全体の性能を示すものではない。

OpenAIの適合度はモデルの生成した推定値であり、JevのNoulと同一の確率特性は検証・保証していない。検索品質全体の比較や全モデルの互換性確認は行っていない。
