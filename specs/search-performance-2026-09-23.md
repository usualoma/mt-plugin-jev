# 自然言語検索の区間計測

実施日: 2026-09-23

## 結論

実際のMySQL上の1,000記事を、実API・候補50件・5件ずつ2並列で検索したところ、検索ハンドラー開始からHTML生成完了まで **6.483秒** だった。最大はJev評価の **3.769秒**。ローカル処理では、保存済みベクトルの数値検証・再正規化が **1.218秒** を占めた。内積計算は **0.088秒**、DB取得とオブジェクト復元は **0.136秒** だった。

「ベクトルDBがないためにDB取得や内積計算が大半を占める」という内訳ではない。まず保存済みベクトルの重複処理が削減候補になる。検索全体ではJevの待ち時間も引き続き大きい。

## 実API・MySQLの計測

- 対象: 開発用MTコンテナー `mt-mt-1` のサイトID 9、記事1,000件、保存済みembedding1,000件。
- 条件: 「国産クラウドへのサイト移行で実際に困ったことがあり、料金や費用には一切言及していない記事」
- 設定: `text-embedding-3-large` / 3,072次元、候補50件、`jev-latest`、5件ずつ、最大2並列。
- 検索ハンドラーとHTML生成を直接実行。記事・設定・索引・ログインセッションを作成・変更せず、画面生成に付随する最近利用したサイトの履歴更新も無効にした。
- 計測範囲にはアプリ初期化、ログイン認証、HTTPサーバーの待ち、ブラウザーへの転送・描画を含めない。管理画面で体感した8秒と完全に同じ範囲ではない。
- 実APIを呼んだのはこの1回。値は通信状況などで変動し、平均値ではない。

| 区間 | 時間 | 全体に占める割合 |
| --- | ---: | ---: |
| Jev評価（5件×10回・最大2並列、送信準備を含む） | 3.769秒 | 58.1% |
| ベクトルの数値検証・再正規化 | 1.218秒 | 18.8% |
| OpenAIで検索文をembedding化 | 0.749秒 | 11.6% |
| 記事・embeddingのDB取得とMTオブジェクト復元 | 0.136秒 | 2.1% |
| 本文のHTML除去・JSON化・ハッシュ計算 | 0.096秒 | 1.5% |
| ベクトルの内積計算 | 0.088秒 | 1.4% |
| 保存ベクトルの展開など（正規化を除く） | 0.053秒 | 0.8% |
| 画面生成・検索制御・その他 | 0.374秒 | 5.8% |
| 合計 | 6.483秒 | 100% |

区間は入れ子の計測時間を差し引いており、正規化時間をベクトル展開時間に二重計上していない。DBの区間はSQLだけでなく、結果の取り出し・MTオブジェクトの復元を含む。

Jevは10リクエストすべて5記事ずつで、実際の同時実行数も最大2だった。各リクエストは 0.668〜0.791秒、通信区間の単純合計は 7.394秒。並列評価の経過時間は 3.769秒であり、今回の測定では並列化が働いている。ただし、この単純合計は別途実測した逐次検索時間ではない。

APIが報告した使用量: OpenAI 47入力トークン、Jev 52340入力トークン。Jevは各リクエストの成功応答に含まれる値の合計。

## 外部APIを除いた確認

同じMySQL上の保存済み記事・ベクトルを使い、OpenAIとJevの通信のみをモックした計測は **1.957秒**。OpenAIのモックベクトルにより候補集合は実API時と異なるが、全1,000件の読込・検証・内積処理は実行している。

別の一時SQLite DBには、リポジトリ内の日本語デモ1,000記事とモックで作った正常な正規化済みベクトルを投入した。検索処理本体を変更せず、計測プロセス内だけで保存ベクトルの再検証・再正規化を省く比較も行った。

| 比較条件 | 3回の中央値 |
| --- | ---: |
| 現行処理 | 1.944秒 |
| 保存済みベクトルの再検証・再正規化を省いた比較処理 | 0.630秒 |

この比較では検索文ベクトルの正規化と保存データのバイト長確認は残している。デモの表示対象50件と順序が一致することも確認した。ただし同じモックベクトルを使った処理時間の比較であり、実データの検索品質や破損データの扱いを検証するものではない。この比較の時点ではプラグイン本体は未変更。後述の最適化では、検証や正規化の精度を保ったまま数値処理を高速化した。

```sh
MT_HOME=/path/to/mt MT_TEST_BACKEND=SQLite \
  JEV_PROFILE=1 JEV_PROFILE_ABLATION=1 \
  JEV_PROFILE_OUTPUT=/tmp/jev-local-profile.json \
  prove -v plugins/Jev/xt/profile-search.t
```

## 最適化後の実装と再計測

保存ベクトルを `unpack` した時点で型は数値に確定している。そのため、3,072次元×1,000件の汎用の型判定・数値の文字列化・正規表現による有限数判定をやめ、数値比較と配列内での正規化に置き換えた。NaN・無限大・範囲外・ゼロノルムの拒否、float32の丸め誤差の補正は維持している。単に再正規化を削除した前節の比較処理とは異なる。

また、Jev用LWPクライアントのkeep-aliveを有効にした。各子プロセス内でHTTPS接続を再利用し、fork前には親プロセスの既存接続を破棄する。候補50件・5件ずつ・2並列の構成は同じ。

同じサイト・検索文で実APIをもう1回呼んだ結果:

| 区間 | 最適化前 | 最適化後 |
| --- | ---: | ---: |
| 検索処理＋HTML生成 | 6.483秒 | 3.410秒 |
| Jev評価 | 3.769秒 | 1.778秒 |
| 保存ベクトルの展開・検証・再正規化の合計 | 1.270秒 | 0.184秒 |
| OpenAI | 0.749秒 | 0.466秒 |

ベクトルの区間は最適化に伴って処理をまとめたため、両方とも `vector_decode.inclusive_seconds`（展開・検証・正規化全体）で比較した。最適化前の「検証・再正規化だけの1.218秒」との直接比較ではない。

Jevは各プロセスの最初のリクエストが約0.76〜0.79秒、2回目以降が約0.23〜0.27秒だった。最適化前は全10回とも約0.67〜0.79秒。APIが返した入力トークン数は今回もOpenAI 47、Jev 52,340で、リクエスト数もOpenAI 1回・Jev 10回だった。

実APIの前後比較は各1回であり、通信状況・API応答・実行環境の負荷によって変動する。OpenAIの処理は変更しておらず、その差は今回の最適化の効果として扱わない。アプリ初期化・認証・HTTPサーバー・ブラウザーは引き続き計測範囲外。

検証:

- 既存DBの1,000件すべてで、従来の正規化処理と最適化後の全成分（double表現のバイト列）を比較し、相違0件。既知の検索ベクトルに対する類似度の相違も0件。
- 単体テストで疎・密なベクトルの値・スコア一致、NaN・正負の無限大・範囲外・ゼロベクトルの拒否を確認。
- ローカルのHTTP/1.1サーバーを使い、2つの子プロセスがそれぞれ1接続で5リクエストを処理し、親の既存接続を継承しないことを確認。
- Perlテスト: SQLite / admin2025、10ファイル・197項目 PASS。
- 配布用tar.gz・zipを再ビルドし、18実行用ファイルすべてが作業ツリーと一致することを確認。
- プラグインの追加依存、スキーマ変更、索引再生成はなし。
